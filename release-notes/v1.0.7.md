## Overview
The Approval Authority Management Microapp is a tenant-scoped hub for viewing approval authority templates and navigating to an approval-authority creation Microapp. This version is the initial GitHub Release baseline identified during repository inspection; no earlier published GitHub Releases or remote release tags were found. Features listed here are present in the repository and should not be represented as newly introduced compared to an unverified earlier release.

## Features included
- Approval authority inventory with authority name, type, latest template version, status, last-updated date, and detail drawer.
- Search by approval-authority name, Active/Draft/Retired status filtering, clearable filter chips, and adaptive pagination.
- Status summary counters for Active, Draft and Retired approval authorities.
- Tenant-scoped retrieval from `approval_templates` and `approval_template_versions`.
- Creator name/email resolution using `useXOAuth().organizationMembers.list()`, avoiding direct organization-member table queries.
- CREATE-gated **Create Approval Workflow** button, launching the child Microapp key `create-authority`; refreshes parent inventory on `create-authority.close` event with created action.
- Responsive desktop table and mobile-friendly UI, loading/error/empty states and selection drawer.

## Security and runtime integration
- `@xoos/microapp-adapter` `0.3.0` registers the `xoos-approval-authority-management` Web Component with isolated Shadow DOM styles and in-shadow toast rendering.
- Runtime context provides user, tenant, client, and scopes; `createXOOSSupabaseClient` loads the `xoos-core` datasource. Standalone preview has a separate preview client, which must not be confused with production runtime authorization.
- CREATE access uses XOOS `useXOOSPermissions()` and `require("CREATE")` before child navigation; backend RLS and tenant-isolation rules remain essential for direct data queries.
- Child navigation passes `parentMicroappKey` through the XOOS Runtime navigation bridge.
- Sensitive tenant/creator identities must follow host authorization and data-protection policy. Client checks do not replace server authorization.

## Known limitations
- XOOS Testing Client Platform browser/runtime validation remains necessary for tenant-scoped inventory, organization-members resolution, CREATE denial/approval, child navigation and close/refetch event, drawer, Shadow DOM rendering and permission boundaries.
- Client-side permission checks are not a substitute for backend policies. Current browser-side queries and cross-tenant boundaries require environment-specific inspection.
- Approval authority editing, approval decisions, and lifecycle changes belong to other Microapps; the current hub should not be described as performing those mutations itself.
- `dist-microapp` checked into historical source is not proof of a release artifact built from the exact approved SHA.
- The application's root `package.json` version is `0.0.0`; the Microapp's actual declared release version is `1.0.7` in `microapp.config.ts`.
